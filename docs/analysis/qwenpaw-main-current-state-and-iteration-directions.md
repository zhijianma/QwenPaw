# QwenPaw main 分支现状、主要矛盾与迭代方向

> 分析基线：`main@1e80734cfcb868bb5ee28cacd8a8f5f20c4d990a`
> 分析日期：2026-09-22
> 分析边界：只分析 main 分支，不包含 `lite-agent-os` 分支的设计与实现。

## 一、结论先行

QwenPaw 当前不是“能力不足”，而是“能力很多，但尚未形成一个清晰、可靠、可验证的产品闭环”。

main 分支已经具备较强的 AgentScope 原生 Agent、工具调用、记忆、Skills、插件、渠道、Coding、权限控制、审计与 Shadow Git Checkpoint 等基础能力。它的真正资产是一个可继续演进的个人 Agent 运行基座，而不是一个单纯的聊天应用或多 Agent 控制台。

当前最突出的问题是：产品中心仍然是 Chat Session 和功能菜单，长期任务的目标、执行状态、审批、证据、产物与验收没有统一在同一个“工作对象”中。结果是个人用户不知道任务是否真的完成，二次开发者不知道应该依赖哪些稳定接口，产品侧也难以解释 QwenPaw 相比 Codex、DSH 等产品的核心价值。

因此，QwenPaw 的下一阶段不应继续横向堆功能，而应聚焦三件事：

1. 让原生 Agent 真正可靠地完成、恢复并验证一项工作；
2. 把安全、审批、审计、Checkpoint 和 Artifact 串成一条可信执行链；
3. 把当前广泛但松散的扩展能力收敛成稳定、平等、可治理的插件契约。

建议的产品定位是：

> 基于 AgentScope 的、本地优先、能够持续完成并验证真实工作的个人 Agent；同时为二次开发者提供稳定、受治理的扩展平台。

## 二、main 分支已经拥有的真实资产

### 1. 原生 Agent 与运行时

- `QwenPawAgent` 基于 AgentScope，已覆盖模型、工具、记忆、Scroll、Tool Guard 与 Coding 等能力。
- Runtime 已具备分阶段生命周期、Hook、Prompt Contributor、工具、模式与中间件等扩展点。
- 这些能力说明 QwenPaw 有条件成为真正的 Agent Runtime，而不必退化为外部 Coding Agent 的壳或多 Agent 聚合应用。

### 2. 安全、治理与恢复基础

- 已存在 Sandbox、Tool/File Guard、Access Policy、Approval、Audit 等组件。
- Shadow Git Checkpoint 是有价值的差异化资产，可为文件操作提供可追踪和可恢复能力。
- 这些模块目前尚未形成端到端体验，但具备构建“可信执行”差异的基础。

### 3. 扩展与生态基础

- 已支持 Skills、插件、渠道、模型与应用类扩展。
- 代码中存在较广泛的 Plugin API 与 Registry，说明项目具有生态化意图。
- 测试资产并不薄弱：基线中约有 785 个 Python 测试文件和 385 个 Console 测试文件。

## 三、从三个角色看当前突出问题

### 1. 个人用户视角

用户需要的不是更多菜单，而是“把一件事情放心交给 QwenPaw”。当前体验的主要问题是：

- 首页仍以 Chat 为中心，`/` 默认进入 `/chat`，缺少统一的工作/任务入口；
- 对话、Goal、Mission、Coding、Cron、Checkpoint、Harness、Approval 等概念并行，用户需要先理解系统内部结构；
- 长任务的计划、执行过程、待审批事项、失败恢复、最终产物和验收结果没有统一呈现；
- 功能虽然丰富，但默认安装和配置认知成本偏高；
- “任务完成”与“模型停止输出”之间缺少明确区分。

用户最终期待的是：说清目标后，系统能展示计划，必要时请求审批，发生错误可以恢复，最终交付可打开的产物和验证证据。

### 2. 二次开发者视角

开发者最看重稳定边界、低成本调试与升级确定性。当前主要问题是：

- Plugin API 很广，但缺少完整、稳定的契约体系，例如 Manifest Schema 版本、权限声明、Contribution 类型、启停/重载策略、健康检查和兼容性规则；
- 内置能力与第三方插件尚未真正遵循同一套装配与治理模型；
- 插件能“接入”不等于能“放心发布”，缺少从创建、调试、验证、安装、升级到回滚的完整开发者路径；
- 部分核心文件体积很大，理解和修改成本高。例如 `react_agent.py`、`model_factory.py`、Workspace/Plugin Registry/Plugin API/Plugin Loader，以及接近 4800 行的 Chat 页面；
- 扩展点较多，但哪些属于长期稳定公共 API、哪些只是内部实现并不清楚。

二次开发者期待的是：用一个清晰 Manifest 声明能力和权限，通过稳定 SDK 接入标准 Slot，无需理解整个仓库即可本地调试、热安装、观测运行状态，并在升级时获得明确兼容性保证。

### 3. 产品与工程视角

当前主要问题不是缺少方向，而是方向过多：

- 产品表面覆盖聊天、记忆、渠道、应用、Coding、Goal、Mission、Cron、Harness 等大量能力，主价值不够集中；
- 多套生命周期和平行状态模型导致体验与工程复杂度同时上升；
- 外部 Harness 在部分路径上直接替代原生 QwenPaw Runtime，而不是作为被治理的执行后端，容易削弱原生 Agent 与安全基座；
- 审批当前包含内存态路径，审计也更偏工具/策略记录，尚不足以支撑跨重启、跨任务的完整责任链；
- 最近 200 个 main 提交中约 99 个为 fix、48 个为 feat，侧面说明复杂度和维护成本已经开始反噬迭代效率；
- 核心依赖约 57 行，继续无边界增加渠道、浏览器、应用和 Harness 会进一步抬高安装与维护成本。

## 四、三个主要矛盾

### 矛盾一：能力丰富，与工作闭环不完整

QwenPaw 已经能调用很多能力，但用户仍难以判断目标是什么、进行到哪里、为何暂停、需要批准什么、产生了什么、是否验收通过。必须从“功能是否存在”转向“工作是否闭环”。

### 矛盾二：扩展面很广，与公共契约不稳定

项目已有插件基础，却还没有把接口稳定性、权限、生命周期、兼容性和开发工具链产品化。继续增加扩展点只会增加隐性耦合，不能自然形成生态。

### 矛盾三：安全组件较强，与可信体验割裂

Guard、Policy、Approval、Audit、Checkpoint 各自存在，但用户还看不到一条完整的因果链。真正的差异不是“有审计模块”，而是每次副作用都能回答：谁发起、为何允许、批准了什么、改了什么、如何恢复、结果是否验证。

## 五、建议的迭代方向

### 方向一：加强 Agent 原生完成能力

保留 AgentScope 和 QwenPawAgent 作为核心，不把 QwenPaw 做成外部 Agent 的启动器。重点改进：

- 目标理解：把用户意图转为明确目标与验收条件；
- 计划：生成可更新、可暂停、可恢复的执行计划；
- 上下文：只注入当前步骤需要的信息，控制上下文膨胀；
- 恢复：工具失败、网络中断或进程重启后可继续；
- 验证：执行后主动检查结果，而不是以模型停止作为完成；
- 委派：外部 Harness 作为受控执行器，由原生 Runtime 统一治理。

### 方向二：建立统一工作对象，而不是再造一套 Runtime

在现有 Runtime 内建立统一的 Work/Task 身份和生命周期，至少包含：

- Goal 与 Acceptance；
- Plan 与当前步骤；
- Run 状态与恢复点；
- Approval；
- Artifact；
- Evidence 与 Verification；
- Event Timeline。

Chat 应成为这个工作对象的一种交互视图，而不是所有状态的唯一容器。Goal、Mission、Coding、Cron 和 Harness 可以保留为不同入口或执行策略，但不能继续各自维护互不相通的事实源。

### 方向三：把安全模块串成可信执行链

形成统一链路：

`Work ID → Tool Call → Policy → Approval → Side Effect → Audit → Checkpoint → Verification`

重点包括：审批持久化、重启后恢复、审计关联 Work/Run/Artifact、Checkpoint 与任务阶段绑定、结果验证记录可查看。这个方向比单纯追逐 Benchmark 更贴近个人用户和企业二次开发者的真实信任需求。

### 方向四：把插件能力收敛为稳定产品契约

建立版本化 Plugin Manifest 与 SDK，明确：

- API/Manifest Schema 版本；
- Tool、Memory、Channel、UI Slot、PawApp、Executor 等 Contribution；
- 权限与资源声明；
- 热加载、需要重启和不支持热更新的边界；
- 健康检查、隔离、禁用和回滚；
- 兼容性测试与官方示例。

应选择真实的官方 Tool、Memory、Channel 和 PawApp 各一个迁移到同一插件契约中，以证明“内置与外部平等”，而不是只提供一个演示插件。

### 方向五：降低默认使用与安装成本

- 默认界面只突出“开始一项工作、查看进行中、处理审批、查看产物”；
- 模型、Agent、Harness、插件内部细节进入高级设置；
- 长尾渠道、浏览器集成、外部 Harness 和重型模型依赖改为按需安装；
- 先收敛一个可靠版本，不同时展开 Lite、Workstation、Hub 三套独立产品实现。

## 六、分阶段优先级与验收

### P0：统一身份与可靠状态

目标：同一工作可贯穿对话、计划、执行、审批、Checkpoint、产物和验证。

验收：刷新或重启后仍能恢复；待审批项在任务视图可见；每个 Artifact 可追溯到执行步骤和证据；状态只有一个事实源。

### P1：原生 Agent 的计划、恢复与验证

目标：QwenPawAgent 能持续完成长任务，而不仅是连续对话。

验收：工具失败可恢复；计划可调整；完成前执行验收；外部 Harness 不绕过安全与审计链。

### P1：稳定插件契约

目标：二次开发者可以在不理解核心实现的情况下发布可靠扩展。

验收：版本、权限、Slot、生命周期、健康与回滚规则明确；至少四类真实官方能力完成迁移；安装后可按声明热生效。

### P2：产品入口与依赖收敛

目标：新用户在低认知负担下完成第一项真实工作。

验收：核心流程无需理解内部概念；可选能力按需安装；首次完成任务的步骤与配置项明显减少。

### P2：场景包与评测闭环

在基础闭环稳定后，再围绕个人知识工作、代码仓库维护等少数场景提供完整方案。评测不仅记录成功率，还要记录恢复率、验收通过率、审批等待、上下文成本与副作用可追溯率。

## 七、现阶段明确不做什么

- 不继续把增加长尾 Channel、Provider、Mode 当作主要竞争力；
- 不把 QwenPaw 做成多 Agent 控制面板或类似 Multica 的聚合应用；
- 不新建一套与现有 Runtime 平行的任务 Runtime；
- 不与 DSH 比拼插件数量，先证明契约稳定和真实插件可迁移；
- 不同时实现 Lite、Workstation、Hub 三条独立产品线；
- 审批仍为临时状态时，不宣称已经具备完整审计闭环；
- 在官方能力尚未按同一契约迁移前，不宣称 SDK 已经稳定。

## 八、最终判断

QwenPaw 与 Codex、DSH 等产品的差异，不应建立在“功能更多”上，而应建立在以下组合上：

1. AgentScope 驱动的原生个人 Agent；
2. 本地优先、长期运行、可恢复；
3. 从权限到审批、审计、Checkpoint、验证的可信执行；
4. 稳定、平等、受治理的插件扩展；
5. 对个人用户简单，对二次开发者透明。

最重要的产品转变是：从“一个拥有很多能力的 AI 助手”，转向“一个能对真实工作结果负责的个人 Agent 平台”。
