Product Strategy · Unified Edition

从 AI 助手，走向 Agent 工作台

QwenPaw 的问题不是能力不足，而是已有能力尚未形成清晰、可靠、 可恢复、可验证并且能够持续复用的产品闭环。

统一产品定位
基于 AgentScope、本地优先、能够持续完成并验证真实工作的 Agent 工作台。

它既服务个人与本地开发，也通过 Hub 承接外部事件和团队协作， 并为二次开发者提供稳定、可治理的扩展平台。

01 · Foundation

已有资产不是起点，而是底座

原生 Agent、安全恢复、扩展生态和工作执行基础已经存在。 下一阶段的任务是统一、收敛，并让能力形成结果闭环。

A01

原生 Agent 与 Runtime

AgentScope、模型、工具、记忆、Coding、Hook 与中间件构成原生运行基础。

A02

安全、治理与恢复

Sandbox、Policy、Approval、Audit 与 Shadow Git Checkpoint 支撑可信执行。

A03

扩展与生态基础

Skills、插件、渠道、模型、应用、Plugin API 与 Registry 已经存在。

A04

工作与自动化基础

Goal、Mission、Cron、Harness、Coding 与 Checkpoint 已覆盖多种入口。

02 · Contradictions

四个结构性矛盾

问题不在于少几个功能，而在于工作对象、可信链路、扩展契约与经验复用没有形成统一结构。

01

能力丰富，工作闭环不完整

用户难以判断目标、进度、暂停原因、待审批事项、产物与验收结果。

02

扩展面广，公共契约不稳定

插件能接入不等于能放心发布，版本、权限、Slot 和生命周期还不稳定。

03

安全组件强，可信体验割裂

Guard、Policy、Approval、Audit 与 Checkpoint 尚未形成完整因果链。

04

任务能完成，经验无法复利

成功流程与失败经验散落在对话中，Cron 也不能代表完整事件自动化。

03 · Product Profiles

同一核心，三种产品配置

三种配置共享 Runtime、领域模型和插件契约，只在部署方式、信任边界与运行规模上不同。

轻量个人 Agent

面向个人和轻量任务，安装后即可完成、验证并交付一项工作。

  • 对话与手动任务，统一任务视图、审批和 Artifact；
  • 简单定时任务与轻量 Skill、Tool、Workflow；
  • 本地优先，不承担公网 Webhook 和组织级调度；
  • 隐藏内部 Agent、Harness 与插件装配复杂度。

本地与内网开发工作台

面向专业开发者与本地技术团队，连接真实工程环境。

  • 多仓库、Git Hook、文件变化、本地事件与定时任务；
  • 长任务、恢复、Sandbox、Checkpoint 与 Coding Harness；
  • 插件开发、调试、热安装、定点验证与健康检查；
  • 连接内网 GitLab、CI，或通过 Relay 接收外部事件。

外部事件与团队协作中枢

面向持续在线的外部集成、多人协作和组织级治理。

  • 公网 Webhook、代码平台、PR、Issue 与 CI/CD；
  • 多用户、多仓库、队列、并发和执行节点调度；
  • 团队权限、审批、审计、配额与组织级知识；
  • Automation、Workflow 与 Plugin 的集中分发。

插件主要在 Workstation 开发、调试和验证，在 Hub 分发、运行与治理；Lite 以安装和使用为主。

05 · Directions

七个迭代方向

七个方向共同服务于一个目标：主动承接工作、可靠交付结果，并将成功转化为后续能力。

D01加强 Agent 原生完成能力+

保留 AgentScope 与 QwenPawAgent 作为核心，建设目标理解、动态计划、按需上下文、失败恢复和主动验证；外部 Harness 是受治理的执行后端。

D02建立统一 Work / Task 对象+

Goal、Acceptance、Plan、Run、Approval、Artifact、Evidence、Verification 与 Timeline 使用同一工作身份。Chat 是视图，Cron 与 Webhook 是触发方式，Harness 是执行策略。

D03串联端到端可信执行+

推进审批持久化、重启恢复、审计关联 Work/Run/Artifact、Checkpoint 绑定任务阶段，以及验证记录可查看。每次副作用都拥有完整因果链。

D04收敛为稳定插件契约+

建立版本化 Manifest 与 SDK，统一 Tool、Memory、Channel、Trigger、UI Slot、PawApp、Executor、权限与生命周期。真实官方能力遵循同一契约，按声明安装生效。

D05建设工作台自动化+

自动化负责从时间或事件创建标准 Work，不是另一套 Runtime，也不能绕过审批、恢复、Artifact 与验证。

TIME-DRIVEN

定时任务

由时间触发，适合日报、周期检查、定期维护和计划性工作。

EVENT-DRIVEN

事件自动化

由 PR、Issue、Push、Review Request、文件变化、任务完成或验证失败触发。

Lite 支持手动和简单定时；Workstation 重点支持本地、Git 与内网事件；Hub 重点支持公网 Webhook、外部平台与团队调度。

D06建立知识与能力复用闭环+

任务结束生成结构化复盘，将成功步骤、失败原因、证据和边界整理为 Knowledge、Checklist、Template、Skill、Workflow、Tool 或 Automation 候选。评分决定是否沉淀，类型路由决定形式，验证门槛决定能否发布。

D07降低默认使用与安装成本+

默认入口只突出开始工作、进行中、审批和产物；内部模型与执行细节进入高级设置。长尾集成和重型依赖按需安装，三种配置共享核心。

06 · Roadmap

P0–P2 路线与验收

先统一事实源和可信执行，再建设稳定扩展、自动化与知识复用，最后扩大 Hub 与场景包。

P0

统一身份、状态与任务视图

对话、计划、执行、审批、Checkpoint、Artifact 和 Verification 贯穿同一 Work。

验收：唯一事实源；重启可恢复；审批可见；Artifact 可追溯；手动与定时使用同一模型。
P1

原生完成能力与可信执行

QwenPawAgent 持续完成长任务，对副作用负责并主动验证结果。

验收：失败可恢复；计划可调整；完成前验收；副作用关联治理链。
P1

稳定插件契约

二次开发者不理解核心实现，也能开发、验证和发布可靠扩展。

验收：契约和生命周期明确；官方能力迁移；安装按声明生效；Workstation 开发，Hub 治理。
P1

工作台自动化基础

定时与事件都能创建标准 Work，并进入相同治理与交付链路。

验收：区分 Cron 与事件；支持 PR、Issue、Push 和内部事件；可解释、去重、暂停、恢复和接管。
P2

知识复用与能力飞轮

经验证的任务经验安全转化为知识、流程、工具和 Automation。

验收：复盘与候选生成；来源可追溯；完成执行、沉淀、复用和反馈闭环。
P2

Hub 与完整场景包

核心闭环稳定后，再承接团队、组织和外部开发平台事件。

验收：Webhook 与集中调度生效；Workstation 成为受治理节点；团队审批、审计与分发生效。

07 · Measures

用结果衡量，而不是用功能数量衡量

核心指标应反映可靠完成、可信执行、自动化效率与能力复利。

  • 结果质量验收通过率、Artifact 可追溯率
  • 运行可靠性失败恢复率、长任务恢复率
  • 可信执行审批、审计与 Checkpoint 覆盖率
  • 自动化价值自动化成功率、人工接管率
  • 能力复用候选采纳率、复用后成功率
  • 使用成本首次完成时间、上下文与执行成本
  • 插件质量安装、升级、禁用与回滚成功率
  • 体验收敛首项工作所需步骤与配置数量

08 · Focus

现阶段明确不做什么

拒绝无边界扩张，保护统一 Work、可信执行与能力复用三条主线。

  • 不把增加长尾 Channel、Provider 和 Mode 当作主要竞争力。
  • 不把 QwenPaw 做成多 Agent 控制面板或聚合应用。
  • 不新建平行的任务 Runtime 或自动化 Runtime。
  • 不把定时任务等同于完整工作台自动化。
  • 不允许 Webhook 或 Harness 绕过统一治理链。
  • 不与竞品比拼插件数量，先证明契约稳定。
  • 不维护 Lite、Workstation、Hub 三套代码分叉。
  • 审批仍是临时状态时，不宣称完整审计闭环。
  • 官方能力未统一迁移前，不宣称 SDK 已稳定。
  • 未经真实复用和验证，不自动升级为正式工具或插件。

Final Position

主动承接工作，可靠交付结果，把每次成功转化为下一次能力。

差异来自 AgentScope 原生能力、统一 Work、可信执行、工作台自动化、稳定插件契约与持续复用飞轮。
